# Session info dialog ('i' hotkey) — design

Date: 2026-08-02

## Problem

Getting oriented on a session today means piecing it together by hand: what
ticket is this, what's actually being worked, what happened in the last few
turns. No single view answers "what is this session and what's it doing"
without opening the transcript or the ClickUp ticket separately.

## Goal

`i`/`I` on the selected row opens a modal with:

1. A deterministic header (name, worktree/cwd, host, updated time) — instant,
   no fetch.
2. If a ClickUp ticket id is detected in the session's name or worktree dir:
   a short plain-English summary of what the ticket is asking for.
3. A short plain-English summary of the last few turns of the session's own
   conversation — "what's actually happening here right now."

Both summaries are generated by piping fetched context into
`claude --model sonnet --effort low --bare -p '<instruction>'` — `--bare`
skips CLAUDE.md/hooks/plugin sync/auto-memory, cutting cold-start cost for a
throwaway summarization call.

## Scope

- **Local sessions get both sections fully.** Remote sessions get both too,
  but the conversation transcript is fetched raw from the remote host over
  HTTP; summarization always runs on the local machine. Remote hosts never
  need `claude` or `cu` installed and never spend their own account's tokens
  — ticket data isn't host-specific either, so the ticket half is identical
  for local and remote rows.
- **No prefetch.** Everything in this dialog fires only on an explicit `i`
  keypress, never speculatively.
- **Read-only.** Nothing here mutates a session, ticket, or transcript.

## Header (instant)

Pulled directly from the already-collected `Session`/`RemoteResult` row —
no fetch, no async:

- Name
- Worktree/cwd (squashed-home display, same as the table's DIR column)
- Host (shown only for remote rows — `Session.Host` is deliberately empty
  for local rows and there is no local-hostname field to show instead)
- `updated: <time>` — `UpdatedAt` if present, else `StartedAt`. Labeled
  explicitly as "updated," not bare "age," since render.go's table already
  uses start-time vs update-time depending on active sort mode and reusing
  that ambiguity here would be confusing.

Branch is **not** shown: it doesn't exist on `Session` (only on
`ResumableSession`, populated by scanning the transcript) and isn't worth a
fetch just for this dialog.

## Ticket section

**Detection**: regex `\bDR-\d{2,6}\b` (Go's RE2 supports `\b` as an ASCII
word boundary — excludes `ADR-123` and `DR-123abc`, which a bare `DR-\d+`
would have matched). Checked against the worktree dir basename first (the
authoritative source — `pickup-next-ticket` names worktrees by ticket id),
falling back to the session Name if the worktree has no match. No match in
either → section omitted entirely, no error shown.

**Fetch pipeline** (id found):
1. `cu fetch --with-comments <id>` (argv, no shell).
2. Its stdout is piped as **stdin** to `claude --model sonnet --effort low
   --bare -p '<fixed instruction>'`. The instruction string is a short fixed
   literal we control ("what is being fixed? short version like i am 25");
   the fetched ticket text — which includes free-text comments an attacker
   or a mischievous teammate could shape — never gets concatenated into the
   prompt argument, only piped as data.

**Failure handling (three distinct outcomes, not two)**:
- No ticket id detected → section omitted.
- `cu fetch` itself fails (network, ticket not found, `cu` missing) →
  `ticket: unavailable (<reason>)`. There's no raw output to fall back to.
- `cu fetch` succeeds but the `claude -p` summarization fails (rate limit,
  timeout) → show the raw `cu fetch` text (truncated) plus a
  `summary unavailable: <reason>` note. The dialog never looks blank.

## Conversation section

**Extraction**: a new dedicated function — not `formatTranscriptTail`
reused as-is, which was the original (wrong) plan. `formatTranscriptTail`
renders `thinking`/`tool_use`/`tool_result` blocks too (preview.go:352-369);
this feature wants conversational text only. The new extractor:

- Tail-scans the transcript (same bounded-buffer `bufio.Scanner` approach
  `formatTranscriptTail` already uses) for `type == "user" || "assistant"`
  entries.
- For `user` entries: the plain string content, or the first text block.
- For `assistant` entries: concatenated `text` content blocks only —
  `thinking`/`tool_use`/`tool_result` dropped.
- Deduplicates streaming assistant re-emissions by `message.id`+`requestId`,
  the same key cost.go already uses for cost accounting (cost.go:81) —
  without this, "last 5 entries" can yield duplicate or fragmentary turns
  from a single streamed response.
- Keeps the last 5 resulting turns, truncated to a total size cap before
  piping (keeps the summarization call cheap and avoids a pathological huge
  prompt).

**Local sessions**: transcript path resolved via the existing
`findTranscript(home, sessionID)` helper (model.go:22-55).

**Remote sessions**: new endpoint `GET /transcript-tail?session_id=<sid>&n=5`
on the server:
- Bearer-auth, same as other endpoints.
- `session_id` format-validated against the existing `resumeSessionIDRe`
  pattern before touching the filesystem.
- Resolves the transcript via the same `findTranscript` helper, server-side.
- Response is bounded: each message's text is capped (same `trunc(...)`
  idiom preview.go already uses), and includes both the transcript's mtime
  **and** size — mtime alone is a weak revision key for a file that may be
  mid-write (stat/read race); `(mtime, size)` together catch a write that
  lands between the two.
- 404 if no transcript is found for that session id.

**Both paths** feed the extracted text to a second `claude -p --bare` call
(same model/effort, same fixed-instruction-in-argv / untrusted-content-via-
stdin split as the ticket pipeline), producing the "like i am 25" summary.

**Failure handling**: extraction or summarization failure →
`unavailable: <reason>`.

## Async fetch mechanics

Reuses `previewPane` (kill_preview.go) for its wake-pipe + snapshot
mechanics — instantiated twice, one per section, so each section loads and
redraws independently and neither blocks the other. Codex review confirmed
merging two wake fds into the modal's `unix.Select` set is sound (kinds
OR together, no lost wakeups, no double-close risk from two independent
instances).

`previewPane.close()` only closes the wake pipe — it does **not** cancel the
fetch goroutine (kill_preview.go:181-197), which was a factual error in the
first draft of this design. Fix: wrap each `previewPane` in a thin
`asyncSection` that also owns a `context.CancelFunc`:

```go
type asyncSection struct {
	*previewPane
	cancel context.CancelFunc
}

func startAsyncSection(title string, run func(ctx context.Context) (PreviewResult, error)) *asyncSection {
	ctx, cancel := context.WithTimeout(context.Background(), infoDialogTimeout)
	pane := startPreviewPane(title, func() (PreviewResult, error) { return run(ctx) })
	return &asyncSection{previewPane: pane, cancel: cancel}
}

func (a *asyncSection) close() {
	if a == nil {
		return
	}
	a.cancel()
	a.previewPane.close()
}
```

`run` wires the context into `exec.CommandContext` for every subprocess in
that section's pipeline, so closing the modal actually kills any in-flight
`cu`/`claude` process rather than leaking it. `infoDialogTimeout` bounds a
wedged subprocess even if the modal is never closed (suggest 20s).

## Rendering

A **new** modal render function modeled on `resumePromptsOverlay`'s
box-drawing and word-wrap (`resume.go:954-1057`, `wrapRunes` at
`resume.go:1101`) — not `kill_preview.go`'s `previewBlock`/
`renderConfirmOverlay`, which are single-block and preview-specific
("preview unavailable" / "pane empty" literals baked in) and weren't built
to lay out two independent, word-wrapped sections plus a header. Layout:
header → separator → ticket section (or nothing, if omitted) → separator →
conversation section. Each section's snapshot (`Loaded`/`Err`/text) is
read independently via its `asyncSection`'s `snapshot()`. Overflow follows
`resumePromptsOverlay`'s existing truncate-with-trailing-"…" rule. Re-laid
out every frame at live width, same as the resume picker (a width baked in
at open time is a documented prior bug there).

Close keys: same as `resumePromptsClose` — Esc, Enter, Left, `q`/`Q`,
Ctrl+C. On close, both `asyncSection`s are closed (cancel + pipe teardown).

## Caching

Repeated or held `i` keypresses must not spawn unbounded `claude -p` calls
— this account already sees recurring 429 pressure from routine polling
(see CLAUDE.md's Usage polling section). Two small, purpose-built bounded
caches (single-flight + TTL, modeled on `usage_cache.go`'s `GetOrFetch`
*shape* — not the literal generic reused, which is tightly coupled to
per-email usage fetches and not a fit here per Codex review):

- **Ticket summary**: keyed by ticket id. TTL ~1h — ticket text rarely
  changes turn to turn.
- **Conversation summary**: keyed by `(host, session id, mtime, size)`. A
  cache hit means nothing new landed since the last summary.

Both: single-flight (a held-down `i` joins the in-flight fetch rather than
starting a second one), bounded size with prune-on-insert (no unbounded
growth from many distinct sessions over a long-running TUI process).

## Security

- Ticket id validated by the tightened `\bDR-\d{2,6}\b` regex before it
  touches any subprocess.
- All subprocess calls via `exec.Command`/`exec.CommandContext` with argv
  arguments — no `sh -c`, no shell string building.
- Untrusted fetched content (ticket text, transcript excerpt) always goes
  to `claude -p` via **stdin**, never concatenated into the `-p` argument
  string, closing a prompt-injection surface a first draft left open.
- New remote endpoint: bearer-auth, format-validated `session_id`, bounded
  response size.

## Testing

Package-var seams for **both** external CLIs — `claude` and `cu` — modeled
on the existing `keychainRead`/`usageInfoFetch` seam pattern, with
`TestMain` defaulting each to panic so no test ever shells out to either
real CLI. (The first draft only seamed `claude`, which would have left
tests able to hit the real ClickUp CLI.)

## Open items for the implementation plan

- Exact `infoDialogTimeout` / per-section fetch timeout value.
- Exact truncation caps (ticket text, transcript excerpt, per-message text
  in the remote endpoint response) — pick concrete numbers during
  implementation, informed by what keeps a `-p` call cheap without cutting
  off useful context.
- Narrow-terminal degraded layout (very small width/height) — follow
  `resumePromptsOverlay`'s existing clip/truncate behavior, verify it holds
  up with three stacked sections instead of one.
